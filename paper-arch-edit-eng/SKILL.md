# Paper-driven Architecture Edit (Engineering)

## 定位

把"论文创新点"翻译成"代码库里的一个可测试的最小改动"，并用验证门保证
改动可回滚、可回归、可复现。讨论是手段，代码是交付。

## 何时触发

- "我想复现 XX 论文的模块，然后改一改用在我们的网络上"
- "论文里的剪枝/冻结/重参数化思路，能不能搬到这个 repo 里"
- "帮我规划一下在现有代码库上加这个分支/删这个层，代码怎么改、怎么测"
- "这个论文创新点在我们 repo 里落地的改造方案，给出 diff 和测试"

不触发：无 repo、无目标论文、纯性能调参、纯 loss 改动。

## 核心纪律（不可跳过）

1. **先定位到代码，再谈创新。** 每个论文机制必须映射到 repo 中的具体
   文件/类/函数/张量形状，否则视为未解构。
2. **改造以最小 diff 为单位。** 每次只加/删一个机制单元，附带回滚点。
3. **每个改动必须有测试。** 至少：单元测试 + 等价性测试（若涉及重参数化）
   + 回归测试（与 baseline 对比的配对基准）。
4. **验证门先于合并。** 随机容量匹配基线、配对种子、随机标签对照作为
   合并前的门；未过门的代码合入时标记 `experimental`，不得进入主分支默认路径。
5. **交付物是代码包。** 报告、讨论记录都是代码包的附属物，不能替代代码。

## 工作流（六阶段，产物逐阶段落到代码）

### 阶段 0 — 论文创新点解构 → `assets/innovation-card.md`

把论文创新点拆成**可工程化的最小机制单元**，每条必须写出：

- 论文原文中的机制描述（一句话）
- 该机制的数学形式（公式或伪代码）
- 该机制在 repo 中的**候选落点**（文件路径 + 类/函数名，允许"待审计"）
- 该机制依赖的**接口契约**（输入张量形状、dtype、是否依赖 BN/初始化、
  是否依赖训练态）
- 若不实现该机制，baseline 行为是什么（用于回滚和对照）

讨论产物：一张创新点卡。未通过"落点可命名"的机制，回退补审计。

### 阶段 1 — 代码库审计 → `assets/repo-audit-table.md`

用 `scripts/repo_scan.py` 扫描 repo，人工补全：

- 目标架构入口、层注册方式、配置系统（yaml/argparse/registry）
- 候选落点所在文件的**接口签名**与**数据流**（上游输出形状、下游期望）
- 现有测试覆盖（该模块是否有单测、是否有等价性测试）
- 依赖与版本约束（torch 版本、CUDA、是否用 torch.compile）
- 是否存在可复用的 hook/插件机制（避免侵入式改动）

讨论产物：审计表 + 一句话结论"机制 M 应落在文件 F 的函数 f，接口为
`f(x: Tensor[B,C,H,W]) -> Tensor[B,C',H',W']`，侵入级别：低/中/高"。

详见 `references/repo-audit.md`。

### 阶段 2 — 改造方案 spec → `assets/change-spec.md`

把审计结论写成**diff 级**改造方案，必须包含：

- **改动单元**：新增文件 / 修改函数 / 替换层 / 加 hook，逐个列出
- **接口变更**：函数签名、配置项、默认值、向后兼容策略
- **回滚点**：git 分支名、feature flag 名、配置开关名
- **依赖变更**：新增 import、版本约束
- **测试计划**：每条改动对应的测试文件与用例名
- **验证门**：本条改动适用哪些门（见阶段 4）

讨论产物：spec 通过评审后，才允许写代码。spec 是讨论的收敛点。

详见 `references/change-spec.md`。

### 阶段 3 — 骨架代码与测试交付

按 spec 实现，强制交付：

- 改动代码（最小 diff，feature flag 包裹）
- 单元测试：形状、dtype、边界（batch=1、空输入、训练/推理态切换）
- **等价性测试**（若涉及重参数化/剪枝掩码）：用
  `scripts/equivalence_test_gen.py` 生成骨架，固定输入、比较输出，
  容差按 dtype 设定，在 SGD 与 AdamW 训练后各跑一次
- 接口契约测试：用 `scripts/interface_contract_check.py` 校验
  上游输出形状/ dtype 与下游期望一致

未附测试的改动不得进入阶段 4。

### 阶段 4 — 验证门 → `references/validation-gates.md`

作为**合并前门**（工程化版的证伪门）：

| 门 | 触发条件 | 未过门的处置 |
|---|---|---|
| 随机容量匹配基线 | 随机特征/门控/掩码补足同等参数与 FLOPs | 代码标记 experimental，禁止设默认开启 |
| 随机标签对照 | 随机标签训练下增益消失 | 同上，并在 PR 中注明机制未验证 |
| 配对种子 | ≥5 种子，\|Δ\| ≥ 2×配对SE | 不得在 README/论文中写"提升" |
| 回归测试 | 与 baseline 在同一套配置下配对对比 | 未跑通不得合入 |
| 等价性（重参数化） | float32 与混合精度下 max diff ≤ 阈值 | 强制阻塞合并 |

用 `scripts/paired_benchmark.py` 产出配对统计与门判定 JSON，附在 PR 中。

### 阶段 5 — 交付包 → `assets/delivery-manifest.md`

交付包必须包含（缺一不可）：

- [ ] 代码：改动分支 + feature flag + 回滚说明
- [ ] 测试：单测、等价性测试、接口契约测试、回归基准脚本
- [ ] 实验入口：一条命令复现 baseline 与改造结果（含随机基线）
- [ ] 配置：yaml/argparse 新增项与默认值
- [ ] 环境：锁文件、CUDA/torch 版本、复现命令
- [ ] PR 描述（用 `assets/pr-template.md`）
- [ ] 讨论记录：创新点卡 + 审计表 + change-spec + 验证门结果
- [ ] 负结果与边界：哪些配置无效、哪些条件下回滚

用 `scripts/delivery_audit.py` 对交付包做机械检查，缺项即失败。

## 讨论如何收敛为代码

每轮讨论必须回答以下三问，否则不算有效讨论：

1. **落点**：这轮讨论改变了哪个文件/函数/接口？（给出路径与签名）
2. **测试**：用什么测试证明这次改动是对的、没破坏 baseline？
3. **门**：这次改动适用哪条验证门，当前是否通过？

只谈"机制更优雅/更符合论文"而不落到上述三问的讨论，标记为 pending，
不进入 spec。

## 判定标准

- 代码可独立跑通 baseline 与改造两条路径，且带 feature flag 可回滚；
- 每条改动有对应测试并通过；
- 验证门结果附在 PR 中，未过门的代码标记 experimental 且非默认路径；
- 交付包机械审计通过。

满足以上四条才允许标记本 skill 任务完成。

## 脚本约定

所有脚本只依赖 numpy/torch/标准库，CLI 传参，输出 JSON + 可读表。
脚本只做检查、生成骨架、跑配对基准，不做实验设计决策。
